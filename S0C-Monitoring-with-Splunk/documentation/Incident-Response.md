# Incident Response

## Overview

This document describes the incident investigation workflow used in the Home SOC Lab.

The investigation process focused on identifying security events, analyzing available telemetry, validating the activity, and documenting the findings.

## Incident Response Workflow

1. Identify
2. Investigate
3. Validate
4. Respond
5. Document

## 1. Identify

Security-relevant events were identified using Splunk searches against Windows Security and Sysmon telemetry.

The main events investigated were:

* Sysmon Process Creation — EventCode 1
* Successful Logon — EventCode 4624
* Failed Logon — EventCode 4625

## 2. Investigate Process Activity

Process creation events were investigated using Sysmon telemetry.

Important fields included:

* Timestamp
* User
* Process Image
* Parent Image
* Command Line
* EventCode

PowerShell and CMD activity were specifically monitored because command interpreters can provide useful security telemetry.

## 3. Investigate Authentication Activity

Windows authentication events were investigated using Event IDs 4624 and 4625.

### Event ID 4624

Event ID 4624 represents a successful logon.

A service logon with **Logon Type 5** was observed during the investigation.

The associated process was:

```text
C:\Windows\System32\services.exe
```

The account observed was the Windows SYSTEM account.

### Event ID 4625

Event ID 4625 represents a failed logon.

A controlled incorrect-password test was performed on the Windows 11 VM.

The test generated a failed interactive logon event with **Logon Type 2**.

A separate network authentication event with **Logon Type 3** was also observed during the controlled lab testing.

## 4. Validate

The observed events were compared with the actions intentionally performed during the lab.

This validation step helped distinguish expected lab activity from activity that would require further investigation.

The failed logon test was intentionally generated by entering an incorrect password once and then successfully authenticating.

Because repeated credential guessing was not performed, the event was not classified as brute-force activity.

## 5. Controlled Security Testing

Kali Linux was used to perform authorized testing against the Windows 11 lab environment.

Activities included:

* Network connectivity testing
* Nmap service discovery
* SMB share enumeration
* SMB protocol enumeration
* HTTP service verification

These tests were performed only within the isolated lab environment.

## 6. Response

The primary response activities in this project were investigation, validation, and documentation.

No destructive actions were performed against the Windows 11 VM.

The project demonstrates the detection and investigation stages of incident response rather than a full enterprise containment and recovery workflow.

## 7. Documentation

Investigation findings were documented using:

* Splunk search results
* Dashboard observations
* Windows Security events
* Sysmon telemetry
* Screenshots
* MITRE ATT&CK mappings

Sensitive values visible in screenshots should be removed or blurred before publishing the project publicly.

## Conclusion

The incident response workflow demonstrated how a SOC analyst can use collected telemetry to identify an event, investigate its context, validate whether it was expected, and document the findings.

The lab focuses on practical monitoring and investigation rather than destructive attack simulation.
